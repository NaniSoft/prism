## Overview

ForgotPassword01 is the screen somebody reaches when they cannot get in: one
identifier field, one control, and a confirmation that says the same thing whether
or not the account exists. Every string is passed in as a prop and the Block ships no
sentence of its own anywhere on the page.

**The decision that makes this a separate Item from Contact01 is that the
confirmation is identical in both cases, and it is expressed in the shape rather than
in the prose.** There is no `found` flag, no `unknown` arm and no second message.
`sent.message` is one sentence and the type has nowhere to put another. A storefront
would add the flag in a single afternoon and ship an enumeration oracle with it: type
any address, press the button, and the reply tells you which of them hold an account
here.

The trade is real and it is argued in both directions, because it is not a clean win:

- A message that differs leaks which addresses are registered. That is an enumeration
  oracle, and it is also the version that tells a reader who mistyped their address
  that they mistyped it.
- A message that is identical teaches a reader who mistyped that they succeeded, and
  on this particular form that is the more common failure, because a recovery form is
  the form a reader is most likely to fill from memory.

The resolution that does not pick a side is a confirmation that names the next step
without confirming the account: it says what was sent and where to look, and it does
not say what was found. That is a sentence your product can write so that it is true
of both cases, and it is the reason `sent.message` is a node and the whole of what
the arm carries. **The words are yours.** A product that decides to take the other
trade can write it in `sent.message` and the Block will not stop it, because a
disclosure decision is not a rendering one; what the Block does is refuse to make the
choice on your behalf by refusing to have a place to put it.

Two other props are required rather than optional, and both are about who is standing
in front of the screen.

| Prop | Why it cannot be optional |
| --- | --- |
| `description` | The confirmation is deliberately the same either way, which leaves the frame as the only place left to say what is about to happen. A reader who mistyped their address is otherwise told nothing, for ever, and concludes the message went somewhere. |
| `onSubmit` | A Block that collects an address and then does nothing with it is a form that takes a personal datum and discards it without telling anyone. |

## Usage

```tsx
import { useState } from 'react'
import { ForgotPassword01 } from '@nanisoft/prism-ui/blocks/forgot-password-01'

export function RecoverAccount() {
  const [identifier, setIdentifier] = useState('')
  const [sent, setSent] = useState(false)
  const [state, setState] = useState<'idle' | 'sent' | 'error'>('idle')
  const [message, setMessage] = useState<React.ReactNode>(null)

  async function recover(value: { identifier: string }) {
    const result = await requestRecovery(value.identifier)
    if (result.refused) {
      setState('error')
      setMessage('The recovery service is not answering. Try again in a minute.')
      return
    }
    setSent(true)
  }

  return (
    <ForgotPassword01
      eyebrow="Account recovery"
      title="Send me a way back in"
      description="We will send a link to the address on the account. If nobody is expecting it, they can ignore it and nothing else will happen."
      identifier={{ label: 'Email address', value: identifier, onValueChange: setIdentifier }}
      submitLabel="Send the link"
      status={state === 'idle' ? undefined : { state, message }}
      sent={
        sent
          ? {
              message: 'If that address is on an account here, a link is on its way to it now.',
              resendLabel: 'Send it again',
              onResend: () => requestRecovery(identifier),
            }
          : undefined
      }
      onSubmit={recover}
      back={{ label: 'Back to signing in', href: '/sign-in' }}
    />
  )
}
```

## Guidelines

### When to use

Use it where a reader has just been refused entry and has to be given a route back.
It is a whole section rather than a dialog, because the reader needs to read the
frame before they type and a dialog is the arrangement that hides it.

Pass `description` even when the frame above it already seems to explain things. This
is the one Block in the family where the sentence under the heading is the only
statement of intent on the page.

Pass `back` wherever there is somewhere to go back to. The link is drawn below the
card, so a reader who changed their mind finds it under the thing they were reading
rather than above it.

### When not to use

Do not use it as a way of asking which addresses hold accounts. If your product needs
to tell a reader that no account was found, that is a disclosure decision with a
security consequence and it belongs in your own copy, deliberately, rather than in a
prop this Block would have grown.

Do not use it to collect a second identifier, a phone number or a security question.
A recovery form that can ask more than one thing has decided something about your
product, and the one thing it must never decide is whether the first answer was right.

Do not use it to report that a resend failed as if it were the first attempt. A
refusal belongs in `status`, which is drawn while the form is up, rather than in
`sent`, which replaces the form.

### Best practices

- Write one confirmation and use it for both cases. The Demo above reaches the same
  sentence whether or not an account exists, and that is the point.
- Leave `status` unset on the press that passes `sent`. The arm has already said the
  outcome; putting the same sentence in both draws it twice on the one screen where
  a reader reads it.
- Use `status` for everything after the first press: a resend that was refused, or a
  resend whose second sentence is worth saying in its own words.
- Pass `value` and `onValueChange` together or neither. A value the Block holds and
  you cannot see is a value you cannot clear, and the reader who mistyped their
  address is the one who most needs to clear it.
- Keep the confirmation about what to do next rather than about what was found. "If
  that address is on an account here, check that inbox" is true either way.
- Do not validate the address inside the Block. It ships no rules, so a field that
  needs one wants your own handler, your own state and your own message.

### Content guidelines

- Name the next step, not the outcome. The reader's question is "where do I look now",
  and the answer is the same whether or not the account exists.
- Do not use the words "we found an account" or "we could not find an account" in the
  confirmation. They are the two sentences this Block exists to make unnecessary.
- Say what will arrive and how long it lasts. A link with a life the reader cannot see
  is a link they will click tomorrow and find dead.
- Say what happens if nobody was expecting it. That sentence is what makes an identical
  message acceptable to a reader who is alert.
- Write the refusal as a fact about the service rather than about the reader: "the
  recovery service is not answering" is true and checkable, "something went wrong" is
  neither.
