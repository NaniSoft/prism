## Overview

ResetPassword01 is the screen where somebody sets a new secret: the secret with a
reveal control, a repeat, a strength note, one control, an announced status region,
and an expired arm that takes the form away. Every string is passed in as a prop.

**`expired` is a first-class arm and it is the state this screen spends most of its
life in.** A reset link has a short life, and the reader who followed one an hour
late is the common case rather than the edge case. So the Block takes the state, draws
your message and your way to ask for a new link, and takes the form away.

The alternative every form-shaped Block reaches for by default is to render the two
fields regardless, let your server refuse on submit, and let your own error boundary
render the sentence. That is a runtime error in your code for a condition this design
system can name, it happens to the reader your product should be kindest to, and it
throws away what they typed. The cost of the arm is that you hold the state and pass
it in. The payoff is that the most frequent thing this screen has to say is a thing the
screen can say.

Three decisions are worth reading before the code.

**The two entries do not compare themselves.** Whether two strings are equal is a
one-line check any Block could do, and doing it here would install a rule in four
products at once and put a fixed sentence about a mismatch beside the field. A product
that says "Those do not match" and a product that says "You typed it differently the
first time" are making different claims about the same fact. So `confirm.error` is
yours and the Block draws none of its own. The cost is named: a caller who passes no
`error` gets a form that submits two different strings and finds out from its own
transport, which is why `confirm` is required here rather than optional.

**The strength note is your function.** The honest reading of a secret's strength
changes as the reader types, and four products rate one on a letter grade, a word, a
count of character classes and a list of breached passwords. It is drawn only once
there is something in the field, because a bar under an empty control is a claim
about a secret nobody has typed yet.

**`autoComplete` is `new-password` here and that is the Block's one platform decision.**
`PasswordField` defaults to `current-password`, which is right for a sign-in and wrong
everywhere else a password appears, and the cost of getting it wrong is an account the
browser then refuses to offer to sign into.

## Usage

```tsx
import { useState } from 'react'
import { ResetPassword01 } from '@nanisoft/prism-ui/blocks/reset-password-01'

export function SetANewSecret({ linkIsLive }: { linkIsLive: boolean }) {
  const [secret, setSecret] = useState('')
  const [confirm, setConfirm] = useState('')
  const [mismatch, setMismatch] = useState(false)

  function strengthOf(value: string) {
    const classes = [/[a-z]/, /[A-Z]/, /[0-9]/, /[^A-Za-z0-9]/].filter((t) => t.test(value)).length
    const raw = Math.min(100, classes * 18 + (value.length >= 12 ? 25 : 0) + Math.min(20, value.length))
    return { label: raw < 40 ? 'Weak' : raw < 75 ? 'Fair' : 'Strong', value: raw }
  }

  return (
    <ResetPassword01
      eyebrow="Account recovery"
      title="Choose a new secret"
      secret={{
        label: 'New secret',
        revealLabel: 'Show the secret',
        hideLabel: 'Hide the secret',
        value: secret,
        onValueChange: setSecret,
        strength: strengthOf,
      }}
      confirm={{
        label: 'Type it again',
        value: confirm,
        onValueChange: setConfirm,
        error: mismatch ? 'Those two are not the same.' : undefined,
      }}
      submitLabel="Save the new secret"
      status={
        mismatch
          ? { state: 'error', message: 'Nothing was changed. Correct the second entry and try again.' }
          : undefined
      }
      expired={
        linkIsLive
          ? undefined
          : {
              message: 'That link has expired. Links last fifteen minutes.',
              requestLabel: 'Send me a new link',
              onRequest: () => {},
            }
      }
      onSubmit={async (value) => {
        if (value.secret !== value.confirm) {
          setMismatch(true)
          return
        }
        await saveNewSecret(value.secret)
      }}
    />
  )
}
```

## Guidelines

### When to use

Use it at the destination of a link you sent, and nowhere else. A link that has not
expired belongs here and nothing else does.

Pass `expired` from the first paint when you already know the link is dead. A screen
that renders a form and refuses it on submit is a screen that wasted the reader's
typing, and the reader who typed was already late.

Keep `strength` as a function. The Demo above rates on four character classes and a
length floor; yours will rate on something else, and a string prop would freeze the
first of those readings.

### When not to use

Do not use it for a reader changing their own secret while signed in. That is a
settings surface with an authenticated session behind it, the link is not involved,
and a product that uses this screen for both has built a recovery flow that a signed-in
reader can reach without a link.

Do not use it to collect anything else. A reset screen that can ask for a phone number
has decided something about your product, and the one thing it must never decide is
whether the first entry was right.

Do not use it to render the mismatch yourself in the status region and leave
`confirm.error` empty. The status region is about the request; the field is about the
entry, and a reader who mistypes twice deserves to be told at the field.

### Best practices

- Pass `value` and `onValueChange` together or neither. A value the Block holds and
  you cannot see is a value you cannot clear.
- Compare the two entries in your handler and put the sentence in `confirm.error`.
  That keeps the rule in one place and the words next to the control they are about.
- Mark the control invalid alongside the sentence. The Block does it for you when
  `confirm.error` is present.
- Treat `done` as the end of the form. The Block takes the fields away, so a caller
  that leaves the status at `done` does not render a form to a reader who has nothing
  left to do with it.
- Do not pass `expired` and a status that is not a refusal. The Block throws, because
  the two together would show a confirmation for a link that is dead.

### Content guidelines

- Write the expiry message as a fact about the link, with its life in it. "Links last
  fifteen minutes" is what makes the refusal acceptable.
- Put the number of minutes in your own words and keep it in step with your own
  configuration. A Block that guessed the lifetime would be guessing about your policy.
- Write the request label as a sentence about what happens next, not as a noun phrase.
  "Send me a new link" can be spoken by a voice control; "Resend" cannot.
- Write the done message as what just changed and what follows from it, including
  whether other sessions were signed out. A reader who has just re-authorised their own
  machine wants to know what else moved.
