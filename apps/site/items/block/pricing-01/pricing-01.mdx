## Overview

Pricing01 is a plan comparison: up to three plans side by side, one of which may
be featured with a primary border, a filled action and a badge. Each plan
carries a name, a price, an optional period, an optional body, a feature list
and one action.

Every string is a prop, including the prices and the words on the action. The block
previously hardcoded a price set and shipped a heading above a title that
already said the same thing.

**A plan's action is a destination or your own control, and it is a union rather
than a label.** `Plan` carried a required `cta` string and the block rendered it as a
`Button`: a focusable control, announced as a button, that activated to nothing, at
the foot of the card a reader was about to decide on. A price is the one number on a
marketing page a reader acts on. An action with an `href` renders as a native
anchor; anything else is the `slot` arm and the block places that node in the card's
foot.

## Usage

```tsx
import { Pricing01 } from '@nanisoft/prism-ui/blocks/pricing-01'

<Pricing01
  title="Pick a plan"
  description="Change or cancel at any time."
  plans={[
    {
      id: 'starter',
      name: 'Starter',
      price: '$0',
      period: ' / month',
      features: ['One project', 'Community support'],
      action: { label: 'Start', href: '/signup' },
    },
    {
      id: 'team',
      name: 'Team',
      price: '$24',
      period: ' / month',
      features: ['Unlimited projects', 'Email support'],
      action: { label: 'Choose Team', href: '/signup?plan=team' },
      featured: true,
    },
    {
      id: 'business',
      name: 'Business',
      price: '$68',
      period: ' / month',
      features: ['Everything in Team', 'Priority support'],
      // A control that is not a link: the caller's own checkout trigger, carrying
      // its own accessible name and its own weight.
      action: { slot: <CheckoutTrigger plan="business" /> },
    },
  ]}
/>
```

`id` is the plan's key and `name` is the word on its card. They are different
facts and they are separate members because two plans can carry the same name, a
monthly and an annual row of one tier, and React is told the cards are ambiguous
the moment they do.

## Guidelines

### When to use

Use Pricing01 when a reader compares a small, fixed number of plans on the same
features. It lays the plans out for comparison and lifts the recommended one.

### When not to use

Do not use it for a usage-based price or a quote. A table of fixed prices cannot
represent a metered plan honestly.

Do not feature more than one plan. Two highlighted plans read as no
recommendation at all.

Do not use the block on a dense application screen. It is a marketing
composition with a lot of vertical space.

### Best practices

- Put the recommended plan in the middle when there are three, so the eye lands
  on it after the first.
- Keep the feature lists the same length across plans. Uneven lists make the
  shorter plan look thinner than it is.
- State the period on every price, or on none. A period on one plan and not
  another invites a wrong total.
- Pass a badge on the featured plan, or none at all. The block ships no badge
  word: a plan that is featured and unnamed is the honest state, and a block
  that hardcoded "Popular" would make that claim for every consumer.

### Content guidelines

- A plan name is one word where possible and takes sentence case.
- Write a feature as an outcome, not a limit: "Unlimited projects" reads better
  than "Projects: unlimited".
- The words on an action are verb-first and sentence case: "Choose Team", "Contact
  sales". A label with no destination is no longer a legal value, so give the action
  an `href` or move it into `slot`.
