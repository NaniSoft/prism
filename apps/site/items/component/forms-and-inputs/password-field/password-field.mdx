## Overview

A PasswordField is a password input with a control that shows what the reader
typed. It is built on `Field`, `Input` and `InputGroup`, so the label, the
helper line, the error and the shared border of the group are the ones this
system already draws.

Two decisions carry the weight. The reveal control is a Component and not a
button a consumer writes, because a toggle with no `type` on a form that submits
on enter posts the form before the reader has read a character, and a toggle with
no name is announced as "button". And the two names it announces are props,
because a reveal control that says "Show password" in a product whose interface
is in another language is the exact defect `check-block-copy` was written to end.

The reveal state is local and is not reported. The value is the same either way,
the field submits the same either way, and a `revealed` prop would be a second
source of truth for a fact only this control cares about.

## Usage

```tsx
import { PasswordField } from '@nanisoft/prism-ui/components/password-field'

const [password, setPassword] = useState('')

<PasswordField
  label="Password"
  description="At least twelve characters."
  value={password}
  onValueChange={setPassword}
  revealLabel="Show the password"
  hideLabel="Hide the password"
  error={tooShort ? 'Use at least twelve characters.' : undefined}
/>
```

## Guidelines

### When to use

Use a PasswordField wherever a reader types a secret: a sign-in, a registration, a
change of password, and the confirmation beside it.

Use it for every password field on a page. A form with one password field that
shows and one that does not reads as though the second is less important, which is
not a thing the system knows.

### When not to use

Do not use it for a one-time code. `OneTimeCode` is segmented, autofills from the
platform and can submit on completion, and none of those survive being wrapped in
a password field.

Do not use it for an API token the reader pasted and cannot retype. A reveal
control on a pasted secret is a control that invites a reader to photograph their
own screen.

Do not build a reveal control beside a plain `Input` to save an import. The
`type="button"` and the two names are the whole reason this Component exists.

### Best practices

- Pass both `revealLabel` and `hideLabel`. They are required, and the second is
  not a state flag the Component derives from the first.
- Pass `autoComplete` on anything that is not a sign-in. `new-password` for a
  registration, a change and a confirmation, so the platform does not offer to
  save a new secret as if the reader were returning to an old one.
- Keep the control controlled. That is what lets a caller clear the field when the
  reader gives up on the form, which is a thing callers need and cannot do
  otherwise.
- Say the length or the rule in `description`, not in the error, until the reader
  has typed something. A rule stated only on failure is a rule the reader meets
  after they have already guessed wrong.
- Never put the entered value into an `error`, a log line or an analytics event.

### Content guidelines

- Write `label` as the field's name: "Password", "New password", "Confirm new
  password". Three fields on one page need three different names.
- Write `revealLabel` and `hideLabel` as the two actions, in the reader's language,
  naming the field when the page has more than one: "Show the password" and "Hide
  the password".
- Write `error` with the rule and the way out: "Use at least twelve characters",
  not "Invalid password".
- Write `description` as the rule before the reader breaks it: "At least twelve
  characters. A passphrase is fine."
