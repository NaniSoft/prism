A settings surface has two halves that are easy to confuse and expensive to get
wrong: the **rail**, which names what can be changed, and the **panel**, which changes
it. Only the panel is a form. Putting the group list inside the form makes every field
a submit, which is a page where a reader cannot leave without losing their work.

`SettingsPage` composes the two and owns nothing else. The rail is a `Sidebar` when
the settings are a product's own, and a `Tabs` row when they are one section's worth.

## The rail names, it does not describe

A group label in the rail is a noun the reader already knows: "Profile", "Billing",
"Notifications". A sentence under it is a claim about what is in it, and the panel
already says that by rendering the fields. Use `Separator` between groups rather than
a heading per group, because a heading in a rail competes with the page's own outline
for a level it does not own.

## One panel, one submit

`SettingsPanel01` takes `groups` from the shared field specification, and each group
is a `FieldSpecGroup` with an `id` the group heading is labelled by. That is what
lets a deep link land on a group and what lets a reader jump between them with a
heading list, so the groups are real headings and not bold text. A field is a
`FieldSpec`, the same field a record write form takes, and a control this package
does not ship is the `slot` arm.

The values are the caller's, and the change handler is where a setting leaves. A
region that applies on change passes an `onValueChange` that applies the mutation
and no save arm, so the panel draws no footer. A region that saves explicitly passes
a save arm and a `submitLabel`.

Fields are `Field` plus `Label` plus one control, and the control is chosen by what
is being edited rather than by what is convenient:

- a short piece of text is `Input`
- a choice from a small fixed set is `Switch` when it is on or off, and a `Select`
  when it is one of several
- something with many options that needs to be searched is `Combobox`

The panel's `headingLevel` sets the depth of the whole outline, groups included, so
moving the panel in a document moves every heading in it. Pass one level deeper than
the page's own section heading.

## The submit is a decision, not a formality

A panel with one field changed and a `Save` button is a page that can lose work. If
the panel holds a single control, change it where it sits and give the panel no
footer at all: `SettingsPanel01` renders no footer when it is passed no save arm and
no `footerStart`. That is the honest state for a toggle, and it is the one most
often got wrong.

The Block ships no revert control, because a setting that applies on change has no
moment at which the value is refused. A caller that wants a rule before the mutation
runs it itself, and a caller that wants a way back keeps the previous value and
offers it in its own control.
