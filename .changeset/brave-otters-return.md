`DocsShell` drew its navigation twice in 0.16.0 and draws it once again

**0.16.0 introduced a regression and this release removes it.** To give a reader below `lg` some navigation, 0.16.0 drew each tree a second time behind a `<details>`: one copy in the rail for a wide screen and one behind a disclosure for a narrow one. Only one of the two was displayed at any width, so the accessibility tree was never wrong and a reader never met two copies at once. Every documentation page in the family still shipped two of everything, and the payload of that is paid on the largest surface the system has.

Three consumer test files failed against 0.16.0 as published, and two distinct defects produced every one of those failures. Two files failed on a count that came back doubled, and two failed on a `getByRole('navigation', { name })` that had two answers where it expects one: the disclosure drew its own `<nav>` under the rail's own accessible name, and that name is how a consumer's suite reaches the rail at all. A suite that holds that a documentation rail contains no disclosure control was never the finding, because the `<details>` was a sibling of the rail in the same frame and never inside it.

**What a consumer measured on 0.16.0, in three built exports.** The Nexus page `/docs/architecture/kanban-service` carried 3 `aria-current="page"` markers where 2 is right, because the third belongs to that site's own bar and the other two are this Page drawing the same page twice. It carried 8 `<nav>` elements where 6 is right, and 52 `data-slot="docs-nav-page"` rows on a corpus of 26. The AlphaLens index at `/docs` carried 12 `data-slot="docs-nav-label"` spans on a six section corpus. The Prism preview route that renders this Page, `apps/site/out/preview/docs-shell.html`, carried 22 `docs-nav-page` rows on an 11 row outline and 5 `<nav>` elements where 3 is right.

**What changes.** Each tree is drawn once, at every width. A documentation page carries one `aria-current` marker, one navigation list per tree and one row per document. Below `lg` the frame is a single column and the rail is its first child, so a reader at a phone or tablet width meets the navigation before the document rather than after it, which is the gap 0.16.0 was reaching for. The Page is still a server Component: no `'use client'`, no hook, no context, no handler, no runtime token read, and no new client JavaScript on any documentation page.

**The fade is now bound to the cut it marks, and it was not.** The fade element was left unprefixed while the `padding-bottom` reserving the band beneath it was already `lg:`-prefixed. The cut exists only where the rail scrolls, which is `lg` and up, so below `lg` the band went inert and the gradient kept painting: the rail's last 2rem carried a fade over the last row or two, permanently, at exactly the width this release starts serving the tree at. Both numbers still matched and no row lost legibility, which is why it survived every lane that was looking. The fade and the band are now written against the same `lg:` as the `max-h`, the `overflow-y-auto` and the `sticky`, so a fade with nothing to fade is no longer painted. **The price, stated rather than left to be found:** below `lg` the rail is bounded by its content rather than by the viewport, so a long tree runs past the fold of a phone screen with nothing marking where it ends. No cut to mark, no band to reserve and no scroll region to scroll inside. That is the honest limit of one copy of the tree at every width, and it is now written into the Page's own documentation beside the rule that causes it.

**The published surface loses two slots.** `data-slot="docs-nav-compact"` and `data-slot="docs-nav-disclosure"` were added in 0.16.0 and are removed here. They were published for exactly one release, and no call site in the four downstream repositories addresses either by name, so nothing there has to change. A call site that reached for one now finds nothing rather than finding an empty region, which is the honest outcome and the reason this is called out. Every slot that existed before 0.16.0 stays, `docs-rail-fade` included.

**What it costs, with the number.** A phone reader now scrolls past the whole navigation to reach the article. One consumer's rail measured 1,318 pixels of content in a built export at 1280 by 680, and those rows wrap on a phone, so the scroll a narrow reader now makes is a thousand pixels or more. That is a real regression for that reader and it is the reason a disclosure was reached for in the first place. It is paid rather than hidden, because the two arrangements that avoid it are both worse: a rail at `lg` and nothing below it reopens the gap 0.16.0 closed, and drawing the tree twice to keep the scroll short is what broke three consumer test files here.

**What would actually remove that scroll.** A collapsed rail below `lg` needs an open state, and a server Component cannot hold one. `<details>` is the only disclosure the platform holds on the Page's behalf, so a control that opens one has to be a client island inside the Page. That is separate work with its own budget and it is not built here: shipping a client boundary to save one scroll is a different trade from the one above, and it belongs in its own change rather than as a side effect of removing a duplicate.

**One Item document was corrected, and no gate reads it.** This Page's own documentation said under Best practices that an entry with no words is a label. That was true before this work and became false the moment the Page began dropping a nameless entry rather than rendering one, and it shipped false through 0.16.0 because nothing in the tree compares that bullet with the Page's own source. The bullet now states what the Page does, and `docs/quality-gates.md` records why no gate was added for it rather than leaving the question open: a gate over prose claims has to enumerate the claims, and a list somebody maintains is the shape that already left the heading gate holding one Block and passing over four, or it has to match on wording, which fires on a rewrite and not on a lie. The decidable half of that failure class has a gate, in the heading-scale table comparison. This half is a reader's, and the hole is now named in the document that collects them.

**Three things 0.16.0 got right and this release leaves as they were, with the fade's bound corrected above.** The rail fade, pinned to a non-scrolling sticky wrapper with the band it covers reserved in `padding-bottom`, both written against the `lg:` that creates the cut; the sticky `max-height` arithmetic in `100svh` rather than `dvh`, which cannot exceed the space it is pinned in; and nameless entries dropped rather than rendered as an empty `<li>`, including the group-label and empty-group arms, counted on each rail as `data-unnamed-entries`.
